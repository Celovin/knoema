\section{Architecture}

Knoema separates persistent state, decision generation, and adapters. Figure~\ref{fig:architecture-flow} summarizes the loop. State modules build an agent-specific context, the decision layer produces an action, and the simulator commits that action to logs, memories, relationship state, and downstream artifacts.

\input{figures/architecture_flow}

\subsection{State Model}

The state model uses simple typed objects. A persona stores identity, background, personality, values, goals, and an opt-in theory-of-mind profile. Short-term memory stores recent local events. Long-term memory stores persisted memories in SQLite and retrieves candidates through a FAISS-compatible vector index. Relationships are directed edges with trust, familiarity, relationship type, and interaction weight. Environment context contains time, location, conditions, and recent world events. Emotion state follows the PAD dimensions of valence, arousal, and dominance. The theory-of-mind module tracks symbolic first-order beliefs and exposes prompt-ready summaries only for personas that enable the feature.

\subsection{Decision Loop}

At every tick the simulator gathers persona, memory, relationship, environment, emotion, and optional theory-of-mind context for an agent. The decision engine renders messages, calls an \texttt{LLMClient}, and parses a strict action structure when possible. Deterministic local clients are used throughout tests and public demos. Provider-backed clients can be added without changing the simulator loop.

\subsection{Scenario DSL}

The Scenario DSL expresses agents, environment, events, duration, metrics, and ethics flags in YAML. The parser returns typed scenario objects, the validator rejects unsafe or unsupported public-safety claims, and the serializer supports round trips for reproducibility.

\subsection{Adapters}

Adapters consume action contracts and logs rather than private runtime internals. The game SDK exposes deterministic NPC responses in Python, TypeScript, and GDScript. Godot and Unity scaffolds demonstrate engine integration paths. Dashboards consume JSONL logs for inspection and replay.

\subsection{Deployment Architecture}

Phase 44 adds a FastAPI server that wraps the simulator pool behind REST and WebSocket interfaces. \texttt{POST /simulations} creates an in-memory run, agent and memory routes expose inspectable state, and \texttt{/simulations/\{id\}/stream} emits JSON log envelopes as ticks complete. Optional bearer-token authentication and an in-memory token-bucket limiter keep the demo surface bounded, while Docker Compose packages the API server with the Streamlit dashboard and research dashboard for a reproducible local deployment story.

\subsection{Cognitive Modules}

Phase 51 adds a persona opt-in hierarchical planning module. Agents with \texttt{planning=False} keep the original tick-level behavior. Agents with \texttt{planning=True} decompose their first active goal into HTN-style tasks, select the next ready task from an inspectable task list, and pass that task into the decision prompt as a planning hint without changing the JSON action schema. The planning-depth experiment reports a 0.900 goal-achievement proxy for three-level hierarchies, compared with a 0.525 planning-off baseline.
